# Terraform code

## Files

Every project root (`projects/<app>/`) has the same files, plus one file per area when `main.tf` grows (`network.tf`,
`database.tf`):

| File | Holds |
|---|---|
| `provider.tf` | `terraform { required_version, required_providers, backend "azurerm" {} }` and the providers |
| `main.tf` | resources and module calls |
| `variables.tf` | inputs, with type, description and validation |
| `locals.tf` | names and values built from the inputs |
| `data.tf` | lookups of existing resources |
| `outputs.tf` | what other code needs |
| `backend/<env>.hcl` | that environment's remote state: storage account, its container, key, Entra ID auth |
| `env/<env>.tfvars` | that environment's values |

## Providers and versions

```hcl
terraform {
  required_version = ">= 1.11"
  required_providers {
    azurerm = { source = "hashicorp/azurerm", version = "5.8.0" }
  }
  backend "azurerm" {} # per environment: terraform init -backend-config=backend/<env>.hcl
}

provider "azurerm" {
  features {}
  storage_use_azuread = true                 # Entra ID, never the storage account key
  resource_provider_registrations = "none"   # the bootstrap registers them; a read-only plan identity can't
}
```

- The subscription comes from `ARM_SUBSCRIPTION_ID`, set per environment by the pipeline: never in code.
- Pin providers exactly, and commit `.terraform.lock.hcl` with the platforms CI and laptops use, so every run uses the
  same provider builds.
- A major provider upgrade (azurerm 4 → 5) is a planned change of its own, with its upgrade guide read first. It
  never rides along with a feature.

## Modules

- A module is one building block for one environment (e.g. a service: its app, identities, roles, migration job),
  called once per project. It lives in `modules/` and is sourced by path.
- When a second repo needs it, it moves to a modules repo and is sourced by tag (`git::…//<module>?ref=vX.Y.Z`).
  Then a version bump is a change of its own, with its plan read for what it changes.
- A module never hardcodes an environment or a secret; everything comes in as variables.

## Variables, names and tags

- Every variable has a `type` and a `description`; values with rules get a `validation` block.
- Names follow the platform's pattern, `<type>-<org>-<app>-<env>-<region>` (registries drop the dashes), built once in
  `locals.tf`, never typed by hand in a resource. Pipelines derive names by the same pattern.
- Every resource carries the platform's tags: app, environment, owner, managed-by.
- `for_each` over a map instead of `count` for anything that isn't a fixed number of identical copies: removing one item
  doesn't shift the others.

## Changing safely

- Stateful resources (databases, vaults, storage) have `lifecycle { prevent_destroy = true }`.
- Renaming a resource or moving it into a module: a `moved` block, so it isn't destroyed and recreated.
- Taking a resource out of Terraform without deleting it: a `removed` block.
- Bringing an existing resource in: an `import` block, applied by the pipeline.
- What a pipeline owns at runtime (a Container App's image, a certificate binding done once by hand) goes in
  `lifecycle { ignore_changes = [...] }`, with a comment that says who owns it.
- `depends_on` only when Terraform can't see the dependency.

## App settings

- An app's non-secret settings (hosts, names, its identity's client ID, public keys) are env vars on its container,
  set here. They change with an apply and take effect on the next revision.
- A real secret goes through a Key Vault reference by name. Terraform never reads or writes its value.
- Values that guard production (the environment name, switches for fakes) are set by the platform per environment,
  never by the app.

## Security

- Private networking and no public network access for databases, vaults and storage, unless a resource must be public
  and says why.
- Databases sign in with Entra ID only (no password exists); the app connects as its managed identity.
- Key Vault with RBAC; each app identity reads only its own secrets.
- Logs go to the environment's Log Analytics workspace through a diagnostic setting, with the workspace's local
  (shared-key) auth off.
- Secrets that the platform generates are never stored as GitHub environment **variables** (anyone with read access
  sees them): they are secrets, or generated by Terraform with write-only arguments.
